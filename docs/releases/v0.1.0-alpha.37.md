# MagicHandy v0.1.0-alpha.37

## Changelog

- The Chat composer now addresses the effective persona selected for the active
  conversation. Selecting Hei, for example, changes the placeholder from
  `Message MagicHandy…` to `Message Hei…`.
- Persona names are resolved by the backend together with each chat-session
  summary. The placeholder therefore follows persona renames and returns to the
  Settings-backed MagicHandy default when a session has no persona or references
  one that has been deleted.
- Persona selection refreshes the active session summary immediately instead of
  waiting for another chat or session operation to update the composer.
- The parameterized placeholder is translated in English, Spanish, Japanese,
  Brazilian Portuguese, and Simplified Chinese.

## Diagnosis And Evaluation

The composer previously rendered one hard-coded `Message MagicHandy…` string.
The persona switcher and prompt composition already used the conversation's
backend-owned `persona_id`, so chat behavior could correctly use Hei while the
entry field still addressed MagicHandy. Copying persona-library state into the
composer would have created a second frontend authority and could remain stale
after a rename or deletion.

Alpha.37 instead adds an effective `persona_name` projection to the existing
chat-session response. The server joins session IDs to its authoritative
persona store, uses the canonical MagicHandy name for the built-in default and
dangling IDs, and returns an empty session collection as `[]` exactly as before.
The Chat route passes that resolved value to the composer and reloads the same
session summary after the persona switcher reports a completed change. Loading,
history-error, and read-only placeholders are unchanged.

Backend regression coverage follows one active session from the MagicHandy
default through binding, renaming, and deleting a persona. Frontend coverage
checks the named and whitespace-fallback placeholders and the route-level data
flow. The complete frontend suite contains 412 passing tests, and the
localization audit covers 1,553 keys across five locales.

The exact-source review app used a fresh isolated database and
`-simulate-motion`; it contained no device credential and left the engine idle.
Reciprocal UI selections visibly produced `Message MagicHandy…` and `Message
Hei…` without a reload or browser error. The configured Ollama
`huihui_ai/granite4.1-abliterated:8b` model then completed a real text-only Hei
chat request in one provider call with a non-empty reply, no repair, no semantic
fallback, and no motion action. No physical-device behavior, acceleration
limit, transport mapping, Stop path, or motion compiler changed in this release.

Full Go tests, vet, zero-issue pinned lint, the pure-Go build, frontend
localization, typecheck/build, and all 412 component tests pass locally. The
PowerShell 5.1 installer and release-policy suite also passes locally; pull-
request and tag CI remain authoritative for race coverage and the exact Windows
installer lifecycle.

The local Go 1.26.4 candidate is 24,209,408 bytes plain and 17,448,448 bytes
release-style stripped. The complete embedded UI is 1,700,091 raw / 804,603
level-9 gzip bytes; HTML/CSS/JS is 1,255,855 / 367,206, and the English startup
path is 812,788 / 214,756. The persona-aware placeholder adds 140 raw / 87 gzip
bytes overall and 170 raw / 81 gzip bytes to startup, with no new dependency or
asset.

## Install Or Update

Download the setup EXE and SHA-256 checksum file from this release. Verify the
checksum, then run setup over the existing installation to preserve
`%APPDATA%\MagicHandy`, including settings, chats, personas, models, patterns,
programs, and optional module state. This release corresponds exactly to source
tag `v0.1.0-alpha.37`.

The Windows setup EXE remains unsigned, Defender-scanned, and lifecycle-tested.
Windows may still show an unknown-publisher reputation warning. Do not bypass a
malware detection; report the exact filename and checksum instead.
